Merkle Commitments with Poseidon in Rust

A public Rust/arkworks prototype for field-element commitments, Merkle roots, membership paths, and verification—with explicit limits on authorship, parameters, and zero-knowledge claims.

Boundary. This is not production cryptography. The threshold comparison is native Rust logic, the current parameters are demonstrative, and the repository has not been security-audited.

What the repository implements

The prototype represents values and randomness as field elements, hashes them into commitments, places the commitments in a Merkle tree, computes a root, generates sibling paths, and verifies membership.

My contribution boundary

The initial core implementation in the public history came from a collaborator. My later work updated parts of the Poseidon, Merkle-tree, proof, example, and documentation surface. The public case study preserves that distinction rather than presenting the repository as an independent implementation.

Why the threshold check is not zero knowledge

The example retains the original values, sums them natively, and compares the result with a threshold. No circuit constrains the relationship between committed leaves and the threshold predicate, and no proof object demonstrates that the committed values satisfy it.

Why the parameters matter

Poseidon security depends on the field, width, rate, capacity, round structure, constants, MDS matrix, and target security level. The current values are demonstrative and must not be described as reviewed production parameters.

Current evidence

  • Public repository and commit history.
  • Documented membership-path construction and verification.
  • README limitations around parameters and the native threshold check.
  • Repository code that can be inspected directly.

Limitations

  • No R1CS or equivalent circuit links commitments, membership, and the predicate.
  • No range constraints define committed values as bounded balances.
  • No reviewed production parameter generation.
  • No security audit or production threat model.
  • Collaborative authorship prevents inferring independent ownership of the initial core.

Minimum credible next version

  1. Define the exact statement to be proved.
  2. Represent values as bounded integers with range checks.
  3. Build a circuit linking commitments, membership, and the threshold predicate.
  4. Use reviewed parameters and document their generation.
  5. Add positive and negative tests, benchmarks, and a threat model.
  6. Record file-level contributions and collaborator approval.
