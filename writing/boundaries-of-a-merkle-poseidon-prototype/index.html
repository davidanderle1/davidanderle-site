Where the Merkle/Poseidon prototype stops

A boundary audit of the public Rust repository: implemented path, missing proof system, demonstrative parameters, and contribution provenance.

  • David Anderle
  • 6 minutes

The repository’s useful core is narrow: it demonstrates how field-element commitments can be placed in a Merkle tree and how a membership path can be generated and verified. The project becomes misleading only when that result is compressed into a broader phrase such as “zero-knowledge balance proof.”

Implemented path

  1. Represent values and randomness as field elements.
  2. Hash each pair through a Poseidon sponge interface.
  3. Use the outputs as Merkle leaves.
  4. Iteratively hash pairs to a root.
  5. Generate sibling paths and verify membership.

Why the threshold check is not zero knowledge

The example retains the original values, sums them natively, and compares the sum with a threshold. No circuit constrains the relationship between committed leaves and the threshold statement. No proof object demonstrates that the committed values satisfy the predicate.

Why placeholder parameters matter

A sponge interface is not secure merely because it is named Poseidon. Round constants, the MDS matrix, field choice, width, capacity, rate, and security target all matter.

Field elements are not balances

A real private-balance statement needs a bounded integer interpretation and range constraints. Without them, a field operation may not correspond to the intended arithmetic domain.

Authorship is part of technical correctness

The initial implementation came from a collaborator. Later commits under my account revised parts of the source and expanded the limitations. That distinction determines what a reader can infer about independent implementation ability.

Minimum credible next version

  • Define the exact statement to be proved.
  • Add bounded integers and range checks.
  • Build a circuit linking commitments, membership, and the predicate.
  • Use reviewed parameters.
  • Add negative tests, benchmarks, and a threat model.
